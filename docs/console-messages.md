# 管理台测试消息与断线重试

2026-11-13。此页记录当前管理台的测试发送行为，不扩展消息路由或写入契约；2026-11-19 新增的投递状态是只读快照，同日补充的优先级、目标设备与模板选择复用既有字段。

“发送测试消息”以 `manual / manual.test` 和所选优先级发送；未选择目标设备时保持既有路由（默认广播到所有已启用设备），默认 `normal`。创建接口为 `POST /api/v1/messages`，`priority` 原本就接受 `low|normal|high|critical`，成功返回 `{messageId}`；首次为 HTTP 201，同一 `connectorId + eventId` 重放为 HTTP 200、返回原消息。消息和投递在原事务中保存，既有 API、鉴权和数据库结构保持。

之前每次点击生成新 `eventId`，服务端保存后若响应丢失，再次发送会变成第二条消息。现在一次逻辑提交持有固定 ID、标题、内容和优先级，收到有效确认后才释放：

- 网络中断、HTTP 408/5xx、成功正文解码失败或缺少有效 `messageId`：结果未知，锁定内容，允许显式“重试同一消息”；不自动重放。
- 明确的其他 4xx 拒绝：保留可编辑草稿，修改后以新 ID 提交。401 仍退出登录。
- 切换导航后恢复尚未确认的表单；发送期间使用原有忙碌门控，不能重复提交。
- 退出登录和认证失效清除待确认 ID、正文与令牌，旧响应不能恢复它们。不写入 localStorage、sessionStorage 或外部存储。

消息详情底部另有[投递批量操作](message-delivery-batch.md)：对当前消息一次性撤销「从未开始发送」的投递或重试「已失败」的投递，先只读预演再确认写入，逐条改动仍记入投递时间线。

## 优先级选择（CONSOLE-29）

表单新增“优先级”：低、普通（默认）、高、紧急。它只决定消息的 `priority`，仍沿用既有路由；DND 行为完全沿用设备既有规则（低/普通只入队不打扰、高亮屏不发声、紧急正常提醒），不新增路由或设备动作。模板测试仍在路由页。

未知结果时优先级与标题、正文一起冻结，导航切回后恢复同一选择；确认成功后清空并回到“普通”，明确 4xx 拒绝则保留可编辑草稿与所选优先级。重试沿用冻结值，即使用户在页面上改动了选项。

## 目标设备选择（CONSOLE-30）

2026-11-19。表单新增可选“目标设备”多选，只列出已启用设备。不选择（空）时不发送 `devices` 字段，保持既有路由与广播语义；选择后只写入这些设备的投递，页脚显示“仅发送到 N 台设备：名称”。服务端请求体新增可选 `devices` 数组，省略或 `null` 与旧请求完全一致：

- 显式列表必须非空、最多 32 项；元素沿用 `[a-zA-Z0-9_-]{1,40}`，重复项去重。空数组由请求校验返回 400。
- 每台设备必须存在且 `enabled=true`；未知或已停用设备返回 400 `invalid_route`，不写消息与投递。
- 同一 `connectorId + eventId` 的重放先取事件级 advisory lock，再比对原投递设备集合（排序去重）：一致返回原消息和 200；集合不同返回 409 `idempotency_conflict`，不追加投递。省略 `devices` 的旧请求仍走原有幂等语义。
- 显式设备绕过路由规则直接投递；这不等同于设备已在线、已展示或已读。投递页的状态与时间线仍是唯一凭据。

未知结果时目标设备与标题、正文、优先级一起冻结，导航切回后恢复同一选择；确认成功后清空回默认，明确 4xx 拒绝保留可编辑草稿与已选设备。重试沿用冻结集合，即使前端选项已变化。

## 模板选择（CONSOLE-31）

2026-11-19。表单新增可选“模板”，选项来自 `GET /api/v1/templates` 的未删除模板；默认“原始文本”，此时不发送 `templateId`，保持原始标题与正文。请求体新增可选 `templateId`，服务端在创建投递时按模板渲染逐设备快照：

- 模板必须存在且未删除，否则返回 400 `invalid_template`，不写消息与投递。渲染复用 `MessageTemplates.render`：`{title}`/`{content}` 等变量、标题 96 字节与摘要 180 字节截断、模板声音与显示时长，事件类型为 `template.<icon>`。
- 与 `devices` 独立组合：显式设备 + 模板只写这些设备的快照；省略设备时按既有路由计算目标后应用同一模板；两者都省略与旧请求完全一致。
- 同一 `connectorId + eventId` 的重放必须保持同一模板：在 advisory lock 内比对原投递的 `template_id`（NULL 也算一种值），不同返回 409 `idempotency_conflict`。显式设备集合仍按 CONSOLE-30 比对；没有投递记录时不追加模板比对。
- 模板只是创建时快照；之后修改或删除模板不改已有投递。显式模板不代表设备在线、已展示或已读。
- 未知结果时模板与标题、正文、优先级、目标设备一起冻结，导航切回后恢复同一选择；确认成功后清空回“原始文本”，明确 4xx 拒绝保留可编辑草稿与已选模板。重试沿用冻结模板，即使页面上改了选项。

## 投递状态（TEST-SEND-RECEIPT-01）

2026-11-19。测试发送获得有效 `messageId` 后，消息页在表单下方显示这条消息的逐设备投递状态；任意消息的详情也显示同一只读视图。读取接口为 `GET /api/v1/messages/{messageId}/deliveries`（`page` 从 1 开始，`size` 默认 `100`、上限 `100`），返回：

- `items[]`：`eventId`、`deviceId`、`status`、`attempts`、`lastError`、`nextAttemptAt`、`receivedAt`、`displayedAt`、`readAt`；
- `counts`：按状态分组、覆盖全部分页的条数；`total`/`page`/`size` 与列表分页一致。未知消息返回 404 `message_not_found`。

页面显示 `共 N 条投递 · 状态计数`，逐设备列出状态、尝试次数、失败原因或下次尝试时间，以及收到/展示/已读时间；「刷新投递状态」重新读取同一消息。投递超过 100 条时只显示前 100 条并标注总数，完整筛选与投递时间线仍在投递页。所有已登录角色可读；撤销/重试仍需 `operate` 权限并走批量接口。该视图是读取时的快照，不轮询、不推断在线状态，也不代表消息已经播放或用户看过。

待确认状态只存于当前页面内存。刷新、关闭页面或退出后无法自动恢复该逻辑提交；此时应核对消息列表，不根据相同正文直接重发。该机制不是跨浏览器的通用幂等提交，也不保证设备已经展示或用户已读。
